## 已获得的正面证据

### 暴击与格挡分支倍率强相容

若使用受击方面板，候选暴伤倍率为 `156.4% − 6.4% = 1.5`，最终固定项为 `91 − 91 = 0`。实测均值比为：

```text
组 2：暴击 / 普通 = 98.25 / 65.2 = 1.5069
组 2：格挡 / 普通 = 19.667 / 65.2 = 0.3016
组 3：格挡 / 普通 = 19.5 / 64.333 = 0.3031
```

因此 `1.5x` 暴击与 `0.3x` 格挡得到三组数据的强支持。不过不同日志可能对应不同攻击随机值，且没有同一随机攻击值下的普通/暴击/格挡配对；故它们仍应标为“强相容”，不是精确服务器常数的最终确认。

### 暴击概率：可作组内压力检查，不能把组间差异归因于暴击

在候选“先格挡后暴击”顺序、双方 69 级的前提下，当前概率式预测组 2 的最终暴击率约 `10.65%`，组 3 约 `9.06%`。但组 3 同时降低技能等级，故 `4/12` 对 `0/11` 不能作为纯暴击概率的组间控制结论。

- 组 2 在候选 `10.65%` 下观察到至少 4 次暴击的概率约为 `3.15%`；这是压力信号；
- 组 3 的 `0/11` 在候选 `9.06%` 下概率约为 `35.2%`，不异常；
- Fisher 双侧检验约 `0.093` 可作为观察描述，但不能用于确认暴击点数函数。

## 对当前单系数主链的正式反证

第 2、3 组是已确认的“暴击 `556 → 518` + 技能等级 `20 → 19`”对照。它不再能单独检验“暴击只影响概率”；但仍能检验候选技能等级项能否解释跨组变化。先用每组全部普通、暴击、格挡跳字，在攻击区间内逐整数枚举、最终显示四舍五入的条件下反解当前完整候选主链，需要把两种模型分开：

- **开启当前候选技能等级项**时，三组各自的普通样本已无解。其原因不依赖攻击方途径专攻/压制具体值：固定的正技能等级项会压缩攻击随机值可产生的相对跨度。组 1 需要 `42.5 / 39.5 = 1.07595`，但最大可解释跨度仅 `1.04910`；组 2 需要 `67.5 / 64.5 = 1.04651`，最大仅 `1.03539`；组 3 需要 `65.5 / 62.5 = 1.048`，最大同为 `1.03539`。因此“当前实现的固定正技能等级项 + 面板攻击区间是普通伤害唯一随机源”被反驳。
- **关闭整个候选技能等级项**时，各组自身可以用一个经验比例拟合普通/暴击/格挡分支；但三组不可以共享一个比例。将技能系数和所有共同未知乘区合为 `B`，在攻击方共同专攻差取最有利的 `0` 时，单组可行区间为：组 1 `0.030390831144–0.030795116431`、组 2 `0.032084329412–0.032664510783`、组 3 `0.031133682614–0.031733656848`，没有两两交集。未知的共同专攻差只会让此类固定攻击项更大，不能恢复组 1/2 的交集。

这项结论依赖用户已确认的共同目标、69 级、烈阳斩单段、无 Buff 与相同未显示条件；组 1、2 取 20 级、组 3 取 19 级。它反驳的是当前**单系数主链结构**，不是单独宣判技能增强、防御或破防公式中的某一项必错。

此前将第 2→3 误记为“仅改暴击”，并由 `68` 与 `62` 推出攻击随机跨度反证；该推论现因技能等级实际从 `20 → 19` 而撤销。候选技能等级项本来就会影响普通伤害，故这两组普通跳字的差异不能再归因于暴击点数。

当前仍成立的结构性反证来自上文的**组内普通样本**：每组的 `min/max` 普通跳字本身就超出“固定正技能等级项 + 已知攻击随机区间”能产生的相对跨度。潜在原因包括：攻击随机模型或其区间不正确、普通分支还有未建模随机项、无括号日志并非同一普通分支、存在尚未记录的状态，或中间取整/技能结构不同于候选链。

## 2026-09-07 复核：技能等级项 ×120 的定量反证与“面板伤害”不可反推战斗系数

本节数值来自此前的专项复现，逐段比较“模型固定技能等级项开启/关闭”时基数的最大相对跨度与实测所需最小跨度（取整边界 `(maxJ-0.5)/(minJ+0.5)`）。该候选模型已从 2.0 稳定主链撤出，专项复现脚本也已从正式项目中移除；当前仅由明确标记的 2.1/2.2 测试分支保留，用于继续验证，不能视为稳定规则。

| 组 | 普通样本 | 实测所需最小跨度 | 模型跨度（技能等级项 ON） | 模型跨度（OFF） |
| --- | --- | ---: | ---: | ---: |
| 1 | `39…43` | `1.07595` | `1.04910`（不可行） | `1.09026`（可行） |
| 2 | `64…68` | `1.04651` | `1.03539`（不可行） | `1.06820`（可行） |
| 3 | `62…66` | `1.04800` | `1.03626`（不可行） | `1.06820`（可行） |

该结论与上文“开启固定正技能等级项时各组普通样本无解”一致，但这次给出可复算数值，并锁定一个具体可检验的嫌疑：`skillPart = 技能系数 × 技能等级 × 120 × 技能增强倍率`（`app.js:204`，`attribute-formulas.json:384`）的相对大小。以组 2 为例，在取最宽松参数（防御倍率上限 `0.75`、专攻差 `0`）时，为容纳 `68` 对 `64`，固定技能项的允许上界约为 `1769`，而模型当前为 `20×120×0.9736 ≈ 2337`，超出约 `1.32×`；若用实际防御倍率 `0.5208` 则超出约 `1.9×`。因此“系数 × 等级 × 120 × 技能增强”作为固定相加项，会把攻击随机跨度压到低于实测所需。

### “面板实际显示伤害”与战斗系数不可互通

资料与代码把“技能说明值（面板伤害）”和“战斗结算”分成两个不同方程：

```text
技能说明值 = floor(技能系数 × (攻击中点 + 120 × 技能等级))            // 只用于展示，见 attribute-formulas.json
战斗 base 伤害 = 技能系数 × (攻击随机 + 破甲差 + 专攻差) × 防御倍率
             + 技能系数 × 技能等级 × 120 × 技能增强倍率               // 战斗实际结算
```

说明值公式不含随机、破甲、专攻、防御、技能增强和其它乘区；用它反推出的系数本质上是“展示系数”，与战斗系数不是同一量。以“净化之斩”同快照为例：说明值 `3227`，攻击中点 `4901`、等级 `20`，说明值反推得 `3227/(4901+120×20) ≈ 0.441994`；而该快照带标签实测（普通 `431`、暴击 `652/655`、格挡 `132/132/133`）在完整候选链下的可行经验系数为 `0.092045982617–0.092415554854`。两者相差约 **4.8×**，正是用户观察到“用面板显示伤害算系数，和实际伤害差距很大”的直接来源：展示系数已被防御与各乘区约压缩到 `1/4.8`，不应直接填回战斗公式。

### 结论

1. “战斗公式中的技能等级项 `×120` 固定相加”被三组各自的普通样本定量反驳；它不是“某个技能系数填错了”，而是公式结构本身嫌疑最大，且对任意使用该结构的技能（含“其他技能”）都成立。
2. “技能面板伤害 → 系数 → 战斗伤害”路径在结构上不可行；展示公式与战斗公式差距约 `4.8×`，必须改为“面板伤害仅作证据”，战斗系数只能由带事件标签的实测反解或手填依据得到。
3. 要真正修正，需要一组**只改变技能等级、其它字段与目标完全不变**的样本（如 19 级 vs 20 级同目标同面板），记录普通/暴击/格挡跳字，即可解出每级真实贡献，进而确定等级项的正确系数与位置，而不是把 `120` 替换成一个猜出来的数。
